# 游戏设计约定

状态：第 0 号剧本已完整接入控制台程序。新文字和菜单交互已通过 .NET 10 Release 构建及 Windows x64 单文件发布。双结局和临时副本的 E01 自删在旧版上验证过；新交互尚未试玩。英文 `Docs/GAME_DESIGN.md` 为准。

## 产品

SOS_Project 是单人文字游戏，呈现为一场控制台会话。玩家阅读叙述，用 W/S 在编号选项间移动，并按 Enter 确认。每段故事是一份剧本模块，结构类似《克苏鲁的呼唤》跑团模组。故事世界是《凉宫春日的忧郁》。玩法是推理解谜。

这是非官方同人项目。不复制小说正文、动画脚本、歌词或官方素材。

## 决定

- 运行时是 .NET 10（`net10.0`）上的 C# 控制台程序。这一版是现行长期支持版本，支持到 2028-11-14。文字和画面都用 `Console.Write` / `Console.WriteLine` 输出。发布目标是 Windows x64 自包含单文件控制台 exe，玩家不必另外安装 .NET。用户现已要求开始实现；`Game/SOS_Project.csproj` 是 C# 工程。本仓库不是 Unity 工程。不添加 Unity 文件。
- 通常的画面是正文。一个场景可以另附一幅由 `■` 和控制台颜色组成的图。这种图只是偶尔出现，不代替朗读文本。
- 程序担任主持人。一名玩家。玩家扮演自己，不是正史角色，也不另起名字。第一份模块的叙述和选项使用中文第一人称；先前的第二人称方向对该模块已被取代。
- 玩家可见的剧情文字逐字显示，显示完毕后才出现选项。按键可立即补完当前文字块；重读已发现材料时立即显示全文。场景给出编号列表，W/S 上下移动列表下方显示的当前选中项；选中后按 Enter 确认。交互游玩不再要求输入选项编号。启动存档菜单也使用相同操作。
- 用来解开或下结论的选项要写明它需要的线索 id，并且只在这些线索已经找到之后才出现。其他选项可以不依赖线索。玩家选中的每一项都要改变局面。
- 有些剧情直接显示全部剧情选项。有些剧情由属性检定决定当前显示哪些剧情选项。选项仍属于这一拍。检定只决定其中哪些看得见。
- 在检定那一拍，玩家选择检定哪项属性。成功和失败各自点名这一拍选项里的一部分。玩家再从显示出来的选项里选一项。没有技能表。属性名称、玩家的数值，以及掷骰或目标值的做法仍未定。同日已取代：检定那一拍不写选项列表，以及检定直接跳进分支。
- 「类似 COC」指本文件里的模块结构。不是采用 Chaosium 规则书、理智值或神话生物数值。
- 剧本的事实来源是符合下列标题的 Markdown。程序使用 `Scenarios/ZeroFloor.Play.cs` 作为从 Markdown 整理出来、编译进程序的明确玩家剧情数据；运行时不解析主持人笔记。
- 第一版完整可玩内容是使用直接选项的第 0 号剧本。该模块不用属性检定或可追踪资源，因此这两套规则仍留给后续系统设计。
- 唯一存档位于 `%LOCALAPPDATA%/SOS_Project/save.bin`。每次剧情选择后自动保存，但送返结局的最后确认除外：清理前保留确认页存档，若结局中断，可再次确认。已有存档时，启动界面提供继续、新游戏或退出；新游戏替换该存档。带版本号的存档保存当前场景、已发现材料、旗标、文本选择和已完成的留下结局。
- 送返结局必须经过剧本中两次明确确认。结局文字显示完毕后，程序删除本作存档。在已发布的 Windows 单文件游戏中，限定范围的辅助进程再尝试于退出后删除自己的 `SOS_Project.exe`；若无法安排，会告知玩家。绝不涉及其他可执行程序或用户文件。从源码运行或在非 Windows 平台运行时，只删存档。留下结局保留两者。

## 模块结构

每份剧本按这个顺序使用这些章节。用不到的章节保留，下面写 `None.`。

1. **标题信息** — 标题、一句话简介、预计游玩时间、玩家角色假设（玩家自己）、语气说明。
2. **主持人简报** — 实际上发生了什么。玩家文本不得包含这部分。
3. **时间线** — 开场时已经成立的事实，按顺序写。
4. **开场** — 玩家看到的、事情为什么开始。
5. **人物** — 每个角色一小节。
6. **地点** — 每个地点一小节。
7. **线索** — 每条线索一小节。
8. **场景** — 可游玩的节拍。进入条件可以是地点、线索或时钟。
9. **选项** — 属于这一拍的剧情选项。
10. **检定** — 可选。玩家选择检定哪项属性。检定结果决定当前显示哪些选项。
11. **结局** — 结局或重大转折。每个都写明被选中的条件。
12. **手稿** — 玩家可以再次阅读的文本，例如传单、便条、文章。

### 人物

- 名字，以及和这件事的关系
- 想要什么
- 知道什么（线索或时间线条目的 id）
- 当众会说什么
- 不会主动说什么（仅主持人）

### 地点

- 第一印象（玩家）
- 主持人笔记
- 谁在这里
- 这里能找到哪些线索
- 玩家接下来能去哪里

### 线索

- 玩家可见的摘要，按「找到时看到的样子」来写
- 在哪里找到
- 若由某个选项揭示，是哪一个选项
- 它指向什么
- 主持人知道的含义
- 若这里由玩家选择检定属性：对应的检定 id

一条线索必须有 id 和揭示条件才算数。埋在散文里的暗示不是线索。直接选项可以揭示它。用检定揭示它的那一拍还要指定一次检定。

### 场景

- 进入条件
- 朗读文本
- 可选画面说明（这幅 `■` 图表现什么，或 `None.`）
- 主持人笔记
- 这一拍的剧情选项，以及每个选项通向哪里
- 显示方式：`直接选项` 或 `属性检定`
- 若是直接选项：显示这份列表。这一拍没有检定。
- 若是属性检定：写下检定 id。检定决定这些选项里当前显示哪些。

### 选项

- 玩家看到的文字
- 出现前需要的线索 id，或没有
- 通向哪里
- 改变了什么

已经出现的选项一旦被选中，就要改变局面。结论类选项在所需线索找到之前不进入列表。

### 检定

- 哪一拍提供这次选择
- 玩家可以选择的属性
- 对其中每一项属性：成功时显示这一拍的哪些选项，失败时显示哪些

掷骰、目标值和完整属性列表还没定。每个结果点名的都是这一拍里已经有的选项。没被点名的选项保持隐藏。

### 结局

- 条件
- 朗读文本
- 之后仍然成立的事实

## 控制台循环（目标）

1. 逐字显示开场或当前场景的朗读文本；按键可补完当前文字块。
2. 如果这一拍有图，用 `■` 和控制台颜色打印它。没有图就跳过。
3. 文字显示完毕后，如果这一拍标明 `直接选项`，就显示它的编号剧情选项。
4. 如果这一拍标明 `属性检定`，就显示属性选项。玩家选择一项属性。结算检定，然后只显示该结果点名的当前剧情选项。
5. 玩家用 W/S 在显示的选项间移动，按 Enter 确认一项剧情选项。
6. 把它结算成叙述，外加一次状态变化：一条线索、一个新场景、一段关系变化，或一个结局。
7. 允许玩家重读手稿和已经找到的线索。
8. 到达结局后停止。

### 第 0 号剧本程序范围

`Game/Program.cs`、`Game/Story.cs`、`Game/GameState.cs`、`Game/StoryRunner.cs` 与 `Game/SaveStore.cs` 分别负责入口、剧情数据、状态、运行循环和单一存档。`Game/OwnFileCleanup.cs` 负责送返结局限定范围的文件清理。运行循环逐字显示剧情文字，按 W/S 选中的编号选项推进场景，处理线索与旗标的条件和效果，允许重读已发现的线索与手稿，并按需打印彩色 `■` 画面。`Scenarios/ZeroFloor.Play.cs` 编译进开场、S00—S16、K01—K10、H01—H04 和 E01/E02。玩家输出不含主持人笔记。

首个模块只用直接选项。本次交互改动之前，成功构建 .NET 10 程序并试玩双结局，观察到临时发布副本在 E01 后退出自删。当前交互随后通过 Release 构建和 Windows x64 自包含单文件发布，尚未再次试玩。未运行自动测试套件。

## 故事边界

下面这些可以作为舞台。以后的剧本不是正式正史。

- 北高、SOS 团活动室，以及学校周围的城镇
- 凉宫春日、阿虚、长门有希、朝比奈实玖瑠、古泉一树
- 这个世界里本来就有的现象，包括封闭空间，以及团里非普通成员已经理解的事实

玩家扮演自己。第一份模块使用第一人称叙述。不把玩家写成正史角色，也不编造姓名或个人经历。

每份剧本都是推理解谜：玩家收集线索，再选择由这些线索解锁的结论。标题信息里的语气说明要写明喜剧与调查压力如何分配。第一份模块以活泼喜剧开场，接近真相时转严肃。

正史角色若出场，说的是为本模块新写的台词。

第一份模块是 `Scenarios/00-zero-floor.md`，舞台为以重庆地貌为灵感、不使用现实地名的虚构中国山城。从《漫无止境的八月》分出的异常世界线把 SOS 团带到 2026 年，并反复穿越 2009—2026 年。时间穿越、异空间，以及与外星科技／资讯统合思念体有关的人工智能，引向玩家在春日创造的世界线中的身世。接近真相之前以喜剧为主。选定的空间路线谜包含跨年代的人际变化与 AI 观测谜。故事以玩家的身份、来处和去向为中心，按八阶段故事圆环推进，最终回到开场外廊选择。双结局是送团员回正常世界线、关闭支线并清理本游戏本地文件，或留在看似真实的创造世界。

玩家看过《凉宫春日》的动画，知道春日可能改写世界。哲学三问须围绕玩家自己的身份、来处，以及自己选择的去向。玩家的动画知识要成为需要验证的证据，也可能使玩家误判；不能把「春日有能力」留到最后当反转。不要给玩家安上编造的个人经历。

## 写作规则

- 玩家可见的句子和仅主持人可见的句子不放在同一段。
- 写原创句子。不誊抄已出版的小说、脚本或对白。
- 真正开始写模块之前，不创建 `Scenarios/`。
- 谜题的结论选项，在它需要的线索 id 找到之前，不放进列表。
- 暗示自然埋进场景叙述与对白。可发现的线索仍在主持人侧写明 id 和揭示条件；应让玩家先凭跨年代证据自己推出最终答案，再由角色说明。
- 每一拍都列出自己的剧情选项，并标明显示方式是 `直接选项` 或 `属性检定`。直接选项显示整份列表，不写检定。属性检定列出玩家可以选择的属性。每一项属性的成功和失败，都要点名当前这些选项里显示哪些。

## 范围之外

- 技能表、理智值，或 Chaosium 的角色卡
- 多人或人类主持人界面

## 未决问题

未来的系统设计仍有下列未决事项。第一份已写模块只使用直接选项，所以属性规则不挡住它的正文。

- 有哪些属性，玩家如何得到这些数值，以及检定如何结算（骰子和目标值，或其他比较方式）。
- 是否存在可追踪资源（压力、怪异度、声望）。不采用理智值。
